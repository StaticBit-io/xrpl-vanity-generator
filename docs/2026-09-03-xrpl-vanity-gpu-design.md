# XRPL Vanity Generator — GPU (CUDA) Backend Design

Status: approved 2026-09-03. Companion to `2026-09-03-xrpl-vanity-design.md`, which
specifies the CPU reference implementation this backend is verified against.

## Background

The CPU implementation (`XrplVanity.Core` + `XrplVanity.Cli`) sustains ~138,000
addresses/second on a 12-thread desktop and exists primarily as the correctness
reference ("etalon") for a GPU kernel. A field-arithmetic spike measured
~3.2e10 multiplications/second mod 2^255-19 on an RTX 5070 Ti, implying a realistic
2–20 million addresses/second once a correct Ed25519 kernel exists — 15–150x the CPU.

The single dangerous failure mode of a hand-written Ed25519 kernel is a **silent
mismatch**: the kernel reports an address that its seed does not actually derive to,
because the field or point arithmetic is subtly wrong on rare inputs. Every decision
below is shaped by making that failure impossible to ship.

## Goals

1. A CUDA backend that derives and searches XRPL Ed25519 addresses at millions per
   second, selectable with `--gpu` on the existing CLI, with match semantics
   identical to the CPU path.
2. Correctness anchored independently of our own code (RFC 8032 vectors) and
   verified at volume against the CPU reference.
3. **No GPU result is ever printed unless the CPU reference independently
   reproduces it.**
4. Toolchain isolation: `dotnet build` never requires CUDA; the .NET solution stays
   pure managed and cross-platform.

## Non-goals

- secp256k1 keys; OpenCL / non-NVIDIA GPUs; multi-GPU; Linux testing (best-effort
  only); cloud CI with a GPU runner; constant-time / side-channel hardening (the
  tool runs offline on the operator's own machine).

## Approach

**.NET host + CUDA driver API via P/Invoke + precompiled PTX.** The entire tool stays
.NET; the only non-C# source is one device-only kernel file. The host calls
`nvcuda.dll` (the driver, present on any NVIDIA machine) directly — no host C++
compiler is needed, which also sidesteps the missing Windows SDK on the reference
machine. The kernel is compiled to PTX **at development time** with NVRTC (the
`nvidia-cuda-nvrtc` pip wheel already used for the spike) and committed as a text
resource; at runtime only the driver is required.

Rejected: a separate CUDA C++ application (needs Windows SDK + C++ toolchain, a
second binary, IPC — foreign to the stack); adopting an existing open-source
Solana-style grinder (untrusted key-generating code; rejected on security grounds).

## Repository layout

```
xrpl-vanity/
  src/XrplVanity.Gpu/            # .NET: driver-API P/Invoke, PTX embedded resource, GpuSearchEngine
  gpu/kernels/xrpl_vanity.cu     # the one CUDA file: device-only, NVRTC-compilable, no host code
  gpu/kernels/xrpl_vanity.ptx    # generated from the .cu; committed; regenerated by the script
  gpu/build-ptx.py               # dev script: NVRTC -> PTX (uses the nvidia-cuda-nvrtc wheel)
  tests/XrplVanity.Tests/        # + GPU tests, auto-skipped when no CUDA driver/device
```

`XrplVanity.Cli` references `XrplVanity.Gpu`. Because P/Invoke resolves at runtime and
the PTX is an ordinary embedded text resource, `dotnet build` works on any machine
without CUDA. `XrplVanity.Gpu` has no package dependencies beyond `XrplVanity.Core`.

The PTX is committed because it is a regenerable text artifact (~100 KB) and the
alternative — requiring NVRTC or nvcc at build or run time — would violate goal 4.
`gpu/build-ptx.py` regenerates it and the README documents the command.

## Device pipeline (per candidate)

The kernel performs exactly the CPU derivation, step for step, so the two paths are
one algorithm:

```
entropy16
  -> SHA-512, first 32 bytes                 (XRPL: entropy -> Ed25519 seed)
  -> SHA-512, clamp lower 32 bytes           (RFC 8032: seed -> scalar a)
  -> A = a * B                               (fixed-base scalar multiplication)
  -> compress A                              (affine via one field inversion; y || sign(x))
  -> 0xED || A32 -> SHA-256 -> RIPEMD-160    (20-byte AccountID)
  -> base58check(0x00 || AccountID)          (double-SHA-256 checksum, XRPL alphabet)
  -> address string (33–34 chars)
  -> match against the uploaded target set
```

### Field arithmetic

Modulus 2^255-19, elements as 8 x 32-bit little-endian limbs, schoolbook 8x8
multiplication into 16 limbs, reduction by folding 2^256 == 38 (mod p) twice plus a
final small fold — the representation benchmarked in the spike (~3.2e10 mul/s). It
is deliberately the simplest correct representation for 32-bit GPU multipliers, not
the fastest possible; performance work belongs to milestone M6 and must not change
the verified results.

Operations: add, sub, mul, sqr (mul(a,a) is acceptable at first), inversion via
Fermat (a^(p-2), a fixed square-and-multiply chain), and canonical reduction for
equality/encoding.

### Point arithmetic and scalar multiplication

Extended twisted Edwards coordinates (X, Y, Z, T) with the standard RFC 8032 /
ref10 doubling and addition formulas; curve constants (p, d, base point B, group
order L) taken from RFC 8032 §5.1.

Scalar multiplication of the fixed base point B is staged:

- **M2 — naive double-and-add** over the 255-bit clamped scalar: ~255 doublings +
  up to 255 additions (~4,300 field multiplications). Simplest to get right and to
  verify bit-for-bit. Ceiling ~7M candidates/s.
- **M6 — windowed fixed-base**: precomputed table of multiples of B (signed 4-bit
  windows, ref10 `ge_scalarmult_base` style), ~64 mixed additions and no doublings
  (~780 field multiplications). Ceiling ~40M candidates/s. Verified against M2 and
  the CPU reference before replacing it.

Point compression: convert to affine with one inversion, encode `y` little-endian
with the sign bit of `x` in the top bit of the last byte (RFC 8032 §5.1.2).

### Hashing

SHA-512 (twice), SHA-256 (three times: pubkey hash and the two checksum rounds),
RIPEMD-160 (once), and base58 encoding by repeated division by 58 — a port of
`XrplBase58.Encode`. All are straightforward device ports verified against the .NET /
BouncyCastle implementations.

### Entropy

For each launch the host draws a fresh 32-byte key from `RandomNumberGenerator`.
Candidate `i` (a 64-bit counter unique within the launch) uses
`entropy_i = SHA-512(launchKey || i)[0..16]`. This is a PRF keyed with a 256-bit
secret — equivalent in strength to the CPU path's per-candidate CSPRNG bytes — and
costs one extra SHA-512 per candidate, negligible next to the scalar multiplication.
The original tool's entropy-mutation weakness is not reproduced. Reported hits carry
their 16 entropy bytes, so the host can re-derive them independently.

## Device-side matching

Matching must run on the device: at millions of addresses per second the host
cannot keep up. To guarantee identical semantics without a second implementation of
the pattern logic, the host builds the target set with the **same
`PatternSet.Builder`** the CPU path uses (normalization, full case expansion with
the 12-character cap, unreachable handling), then flattens it for upload.

`XrplVanity.Core.PatternSet` gains one accessor for this purpose: an enumeration of
its expanded targets as `(MatchPosition Position, string Value)`. The Builder's
logic remains the single source of truth; the GPU consumes its output.

On the device: targets are grouped by (position, length); `starts` and `ends`
buckets are sorted and searched with binary search over the address slice;
`contains` targets are checked with a substring scan (contains lists are small in
practice; a large list is linear and documented as such). Targets live in device
global memory, uploaded once per run.

### Hit reporting and the re-verification gate

The kernel writes only matches (rare) into a fixed-size device buffer of hit slots
(entropy16 + address chars) behind an atomic counter. The buffer holds 4,096 slots
per launch — orders of magnitude above the expected hits per launch for any
realistic pattern set; if a launch ever fills it, the surplus hits for that launch are
dropped and the host reports the overflow count to stderr, so the loss is visible
rather than silent. After each launch the host reads the count and the slots.

**Every hit is re-verified on the host** with the CPU reference: the host runs
`CandidateEvaluator.TryEvaluate` on the hit's entropy bytes and prints the
(address, seed) pair **only if** the CPU derives the same address and its matcher
also reports a match. A disagreement is never printed; it is counted and reported to
stderr as a GPU consistency error. Consequence: a latent GPU arithmetic bug can cost
throughput, never a wrong key.

The kernel also has a **verification mode** that writes the derived address for
every candidate (not only hits); it exists for the volume cross-check below and is
not used by the search path.

## Host (.NET) side

`XrplVanity.Gpu`:

- `CudaDriver` — minimal P/Invoke surface over the driver API: `cuInit`,
  `cuDeviceGetCount`, `cuDeviceGet`, `cuDeviceGetName`, `cuDeviceGetAttribute`,
  `cuCtxCreate`/`cuCtxDestroy`, `cuModuleLoadDataEx`, `cuModuleGetFunction`,
  `cuMemAlloc`/`cuMemFree`, `cuMemcpyHtoD`/`cuMemcpyDtoH`, `cuMemsetD8`,
  `cuLaunchKernel`, `cuCtxSynchronize`, `cuEventCreate`/`cuEventRecord`/
  `cuEventSynchronize`/`cuEventElapsedTime`, `cuGetErrorString`. Library name resolved
  at runtime (`nvcuda` on Windows, `libcuda.so.1` on Linux) via `NativeLibrary`.
- `GpuSearchEngine` — loads the embedded PTX, uploads the flattened targets, runs
  launches in a loop (fresh launch key each time), drains hits, re-verifies them via
  Core, and exposes the same match stream the CPU runtime produces. The number of
  candidates per launch is an internal constant (chosen at M0/M4 to saturate the
  device — on the order of a few million), not a user-facing option in v1.
- PTX is compiled for baseline `compute_75` (Turing, 2018+); the driver JIT-compiles it
  for the actual GPU, so the reference RTX 5070 Ti and any modern NVIDIA card both
  run it.

CLI: a `--gpu` flag selects the GPU engine. All other flags, the output format, the
secret warning, `--count`/`--out`, and the exit codes are unchanged. If no CUDA
driver or device is available, `--gpu` prints a clear error and exits 2 — it does
**not** silently fall back to CPU, which would misrepresent the speed the operator
asked for.

## Correctness strategy — four independent anchors plus the runtime gate

1. **Field arithmetic** — `fe_mul`/`fe_sqr`/`fe_inv`/`fe_add`/`fe_sub` compared with
   `System.Numerics.BigInteger` on random inputs and edge values (0, 1, p-1, p, 2^255-1,
   values with all-zero and all-one limbs).
2. **Ed25519 against RFC 8032** — the standard's §7.1 test vectors give secret key →
   public key pairs (e.g. TEST 1: secret
   `9d61b19deffd5a60ba844af492ec2cc44449c5697b326919703bac031cae7f60` → public
   `d75a980182b10ab7d54bfed3c964073a0ee172f3daa62325af021a68f707511a`). The device
   scalar multiplication + compression must reproduce them. This anchor is
   independent of every line of our own code.
3. **Hashes** — device SHA-512, SHA-256 and RIPEMD-160 compared with .NET /
   BouncyCastle on random inputs of the exact sizes used (16, 32, 33, 21 bytes).
4. **Volume cross-check** — the kernel's verification mode over a fixed, seeded set
   of 1,000,000 entropies; every device address must equal `BouncyCastleDeriver`'s.
   Re-run at every milestone that touches the pipeline.

Plus the permanent runtime gate of the previous section. The GPU path is therefore
trustworthy to exactly the degree the CPU reference is.

GPU tests live in the existing test project and are skipped (xUnit v3 `Assert.Skip`)
when `cuInit` fails or no device is present, so the suite stays green on machines
without CUDA.

## Milestones

Each milestone is an independently testable deliverable with a correctness gate.

| Milestone | Deliverable | Gate |
| --- | --- | --- |
| M0 | `XrplVanity.Gpu` project, driver P/Invoke, PTX load, trivial kernel, device detection, `build-ptx.py` | kernel runs and returns expected data; tests skip cleanly without CUDA |
| M1 | Field arithmetic on device | anchor 1 |
| M2 | Point ops, naive fixed-base scalar mult, compression | anchor 2 + agreement with BouncyCastle on random scalars |
| M3 | SHA-512, SHA-256, RIPEMD-160, base58 on device | anchor 3 |
| M4 | Full entropy → address pipeline + verification mode | anchor 4 (1,000,000) |
| M5 | Device matching, hit buffer, host re-verification gate, `--gpu` in the CLI | end-to-end; semantics identical to CPU on shared target sets |
| M6 | Windowed fixed-base table | anchors 2 and 4 re-run; benchmark |

M0–M5 establish correctness; M6 is the speed step. This is expected to be two
implementation plans: **Plan A (M0–M4)** "the math is proven", **Plan B (M5–M6)**
"integration and speed".

## Expected results and risks

Expected throughput on the reference machine: M5 ≈ 2–4M addr/s (15–30x CPU),
M6 ≈ 10–20M addr/s (70–150x CPU). These are planning figures; the spike's
3.2e10 mul/s is an arithmetic ceiling, and a real kernel loses a factor of 2–4 to
hashing, memory traffic and register pressure.

Risks: (1) a subtle arithmetic error on rare inputs — mitigated by the four anchors
and eliminated as a shipping risk by the runtime gate; (2) throughput below
expectation from register pressure — addressed in M6, never affects correctness;
(3) PTX/driver JIT differences across GPUs — mitigated by the conservative
`compute_75` baseline and by running the volume cross-check on the target machine.

## Assumptions made on the operator's behalf

Any of these can be reversed before implementation starts.

1. `--gpu` is a flag on the same CLI, not a separate executable.
2. Correctness before speed: naive scalar multiplication first, the windowed table
   last.
3. Without an NVIDIA driver, `--gpu` fails loudly (exit 2) rather than silently
   running on CPU.
4. Any NVIDIA GPU from Turing (2018+) is supported, not only the reference card.
5. Windows is the primary platform; Linux is best-effort and untested.
6. Every printed GPU result is re-verified by the CPU reference (a small cost for a
   hard guarantee).
